# 버그 리포트를 재현 가능한 링크로 바꾼 방법

사내 운영툴에서 QA가 발견한 버그를 전달받으면 먼저 해당 계정을 검색했습니다. 그다음 전달받은 설명에 맞춰 탭을 열고, 그 안에서 문제가 발생한 기능을 다시 찾았습니다. 설명이 정확해도 전달한 사람과 받은 사람이 서로 다른 계정이나 탭을 보고 있으면 확인이 처음부터 다시 시작됐습니다.

처음에는 버그 설명을 더 자세히 쓰면 해결될 줄 알았습니다. 그래도 계속 빠지는 상태가 하나 있었습니다. **어느 계정의 어느 화면을 보고 있는가**였습니다. 증상은 여전히 글로 설명해야 했지만, 화면 위치까지 사람이 다시 옮겨 적을 필요는 없었습니다.

이 글은 회사와 서비스를 드러내지 않기 위해 실제 화면 이름, URL과 코드를 사용하지 않습니다. 당시의 문제와 상태 책임을 가상의 이름과 구조로 단순화했습니다.

## 같은 버그인데 서로 다른 화면을 보고 있었다

기존 버그 전달에는 계정 ID, 탭과 사용한 기능이 자연어로 들어갔습니다. 화면 상태를 바로 여는 링크가 없어서 설명을 받은 사람이 그 상태를 직접 다시 만들어야 했습니다.

클릭 몇 번이 늘어나는 데서 끝나지 않았습니다. QA와 개발자가 서로 다른 위치를 보고 있으면 어느 화면에서 증상이 발생했는지 다시 묻고 답해야 했습니다. 버그 자체를 확인하기 전에 화면 위치부터 맞추는 왕복이 생겼습니다.

## 설명을 더 자세히 쓰는 것으로는 해결되지 않았다

설명을 길게 쓰면 한 번의 전달은 더 정확해집니다. 그래도 QA는 버그를 발견할 때마다 계정 ID와 화면 경로를 같은 형식으로 다시 작성해야 했습니다. 화면 구조가 바뀔 때마다 설명 방식도 바뀌었고, 받은 사람은 자연어를 읽은 뒤 같은 경로를 다시 실행했습니다.

그래서 전달할 정보를 둘로 나눴습니다.

- 어떤 동작에서 어떤 증상이 발생했는지는 사람이 설명한다.
- 어느 계정과 화면 위치에서 확인했는지는 브라우저 주소가 전달한다.

증상과 재현 절차는 계속 사람이 설명했습니다. URL이 맡은 범위는 계정과 화면 위치였습니다. 버그 리포트를 자동화한다는 넓은 목표 대신, 다른 사람이 같은 위치로 들어오게 하는 문제만 해결하기로 했습니다.

## 화면 위치를 URL이 맡게 했다

계정과 탭, 세부 위치를 URL에 담았습니다. 아래 주소는 실제 구조를 설명용으로 단순화한 예시입니다.

```text
/accounts?accountId=42&tab=activity&panel=details
```

이 주소에서 `accountId`는 조회할 계정을, `tab`과 `panel`은 화면에서 열 위치를 정합니다. 검색 결과에서 계정을 골라도 같은 URL이 만들어집니다. Slack에서 복사한 링크 역시 같은 경로로 진입합니다.

별도의 “공유하기” 기능은 만들지 않았습니다. QA는 이미 Slack에서 링크를 주고받고 있었습니다. 브라우저 주소를 그대로 복사하게 하니 새로운 사용법을 익히거나 공유용 데이터를 따로 관리할 필요가 없었습니다.

## 왜 localStorage를 사용하지 않았나

먼저 `localStorage`를 검토했습니다. 마지막으로 보던 탭을 저장하면 같은 사람이 돌아왔을 때 이전 화면을 복원합니다. 개인의 작업을 이어가는 용도라면 맞는 선택입니다.

개인의 마지막 상태를 복원하는 경우와 달리, 이번에는 링크를 받은 다른 사람이 같은 화면을 열어야 했습니다. `localStorage`는 브라우저 안에 남으므로 상대방에게 특정 계정과 탭을 전달하지 못합니다. 여러 계정을 오가면 이전 작업 맥락이 현재 링크와 섞일 수도 있습니다.

URL과 `localStorage`는 둘 다 상태를 보존하지만 전달 범위가 다릅니다.

| 기준                            | URL              | localStorage        |
| ------------------------------- | ---------------- | ------------------- |
| 같은 브라우저에서 다시 열기     | 가능             | 가능                |
| 다른 사람에게 같은 위치 전달    | 가능             | 불가능              |
| 새 탭과 외부 링크에서 위치 확인 | 주소에 드러남    | 별도 복원 과정 필요 |
| 이번 문제와의 관계              | 공유할 화면 위치 | 개인의 마지막 상태  |

`localStorage`는 개인의 마지막 상태를 복원할 때 맞습니다. 이 사례에서는 상대방에게 같은 위치를 전달해야 했으므로 URL을 선택했습니다.

## URL과 TanStack Query의 책임을 나눴다

계정 데이터 전체는 URL에 넣지 않았습니다. URL은 어디를 열지 정하고, TanStack Query는 해당 식별자로 서버 데이터를 다시 조회합니다.

<StateOwnershipDiagram locale="ko" />

아래 코드는 당시의 상태 책임을 가상의 이름과 구조로 단순화한 예시이며, 실제 업무 코드는 아닙니다.

```tsx
type ReproductionLocation = {
  accountId: string;
  tab: 'summary' | 'activity';
  panel?: 'details';
};

const reproductionLocation = parseReproductionLocation(searchParams);

const accountQuery = useQuery({
  queryKey: ['account', reproductionLocation.accountId],
  queryFn: () => fetchAccount(reproductionLocation.accountId),
});

return (
  <AccountScreen
    account={accountQuery.data}
    tab={reproductionLocation.tab}
    panel={reproductionLocation.panel}
  />
);
```

여기서 URL은 화면 위치의 기준입니다. TanStack Query cache는 `accountId`에 해당하는 서버 데이터를 관리합니다. 링크를 공유해도 조회 당시의 데이터까지 복사되는 것은 아닙니다. 링크를 연 시점의 서버 데이터를 다시 가져옵니다.

책임을 이렇게 나누자 검색, 새 탭과 외부 링크 진입이 모두 같은 흐름을 사용했습니다. 진입 경로마다 별도의 복원 코드를 두지 않아도 됐습니다.

## 모든 상태를 URL에 넣어서는 안 된다

화면 상태를 공유하려면 URL에 담기 전에 노출 위험부터 따져야 합니다. 브라우저 주소는 기록, 서버 로그, 화면 공유와 메신저에 남습니다. 인증 정보, 비밀값과 입력 중인 민감한 내용은 URL에 두면 안 됩니다.

URL에 넣을 상태는 세 가지 질문으로 골랐습니다.

1. 다른 사람이 같은 위치로 들어올 필요가 있는가?
2. 주소에 노출돼도 안전한가?
3. 데이터를 찾을 식별자와 화면 위치만 담는가?

세 질문을 모두 통과한 계정 식별자와 화면 위치만 URL에 담았습니다. 링크를 안다고 데이터 접근 권한이 생기는 것도 아닙니다. 링크로 진입해도 기존 인증과 권한 검사를 그대로 통과해야 합니다.

입력 중인 폼, 스크롤 위치와 조회 당시 데이터까지 완전히 재현하는 것은 이 사례의 범위가 아니었습니다. 그런 상태까지 URL에 넣으면 주소가 현재 화면을 설명하는 계약에서 벗어나 화면 내부 구현을 그대로 노출하는 저장소가 됩니다.

## 검색과 딥링크가 같은 경로를 타는지 검증했다

URL을 화면 위치의 기준으로 삼은 뒤에는 잘못된 주소도 다뤄야 했습니다. 검색과 직접 링크처럼 진입 경로가 달라도 같은 계약을 따라야 했습니다. 구현 뒤에는 이 세 동작을 자동 테스트로 고정했습니다.

| Given                                  | When                   | Then                                      |
| -------------------------------------- | ---------------------- | ----------------------------------------- |
| 유효한 계정 ID와 화면 위치가 있는 링크 | 링크를 직접 연다       | 해당 계정, 탭과 세부 위치가 열린다        |
| 검색 결과에서 계정을 선택한다          | 계정 화면으로 이동한다 | 딥링크와 같은 URL 진입 경로를 사용한다    |
| 잘못된 계정 ID가 URL에 있다            | 계정 조회가 실패한다   | 공통 오류 경계에서 잘못된 진입을 처리한다 |

공유한 상태가 복원되는지, 검색과 링크 진입이 서로 다른 구현으로 갈라지지 않았는지 확인했습니다. URL은 사용자가 직접 바꿀 수 있으므로 잘못된 계정 ID도 공통 오류 경계에서 처리하는지 검증했습니다.

정상적인 링크만으로는 URL 상태를 충분히 검증하지 못합니다. 잘못된 식별자와 존재하지 않는 계정도 외부 입력으로 보고 안전하게 처리해야 했습니다.

## 링크가 실제 전달 방식으로 자리 잡았다

기능을 배포한 뒤 QA는 여러 버그를 전달할 때 Slack에 현재 화면 링크를 반복해서 붙였습니다. 링크를 받은 사람은 같은 계정, 탭과 세부 위치로 바로 들어갈 수 있었습니다. 링크가 포함된 리포트에서는 계정을 다시 검색하거나 서로 다른 위치를 보고 재확인하는 왕복을 피했습니다.

처리 시간과 문의 수의 변화는 측정하지 않았습니다. 모든 버그 전달의 왕복이 사라진 것도 아닙니다. 증상과 재현 동작은 여전히 설명해야 했습니다. 화면 위치를 다시 찾는 과정은 링크로 바뀌었고, QA는 실제 전달에서 그 링크를 반복해서 사용했습니다.

별도 교육은 필요하지 않았습니다. QA가 이미 하던 링크 공유에 화면 상태를 함께 실었고, 실제 업무에서도 계속 그 방식을 사용했습니다.

## 운영툴에서는 화면만큼 다시 들어오는 경로가 중요했다

이 작업 전에는 운영툴의 화면 안에서 무엇을 더 빨리 찾게 할지 주로 생각했습니다. 계정 검색을 줄이고 탭을 정리하는 일도 중요합니다. 실제로 QA와 개발자는 화면을 혼자 한 번 보고 끝내지 않았습니다. 발견한 상태를 다른 사람에게 넘기고, 시간이 지난 뒤 다시 들어왔습니다.

URL에 계정과 화면 위치를 둔 뒤에는 현재 무엇을 보여주는가와 이 상태로 어떻게 다시 들어오는가를 함께 보게 됐습니다. Slack에서 링크를 받고 다시 진입하는 과정까지 제품이 책임져야 할 경로로 보기 시작했습니다.
