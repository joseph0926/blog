# DOMPurify를 업그레이드했는데, 왜 happy-dom을 고쳐야 할까

## lockfile을 지웠을 뿐인데

[firsttx](https://github.com/joseph0926/firsttx) 모노레포의 pnpm을 11로 올리는 작업을 하고 있었습니다. packageManager 버전을 올리고, package.json에 있던 `pnpm.overrides`를 pnpm 11 계약에 맞는 위치인 pnpm-workspace.yaml로 옮기는 작업이었습니다.

여기서 익숙한 행동을 하나 했습니다. pnpm-lock.yaml을 지우고 `pnpm install`을 실행한 것입니다. 어차피 pnpm 메이저를 올리는 김에 lockfile도 새로 깔끔하게 만들자는 생각이었습니다.

이 설치 한 번이 이 글 전체의 발단이 됐습니다.

lockfile이 없는 상태에서 설치하면 package.json의 캐럿(`^`) 범위가 전부 다시 해석됩니다. 이 재설치로 vitest는 4.0.18에서 4.1.10으로, eslint는 9.39.2에서 9.39.4로 올라갔고, typescript-eslint와 prettier도 함께 움직였습니다. 그리고 dompurify가 3.3.1에서 3.4.11이 됐습니다. 제가 의도한 변경은 "pnpm 설정 이관" 하나였지만, 실제로 일어난 변경은 "설정 이관"과 "의존성 그래프 전체 갱신" 둘이었습니다.

그리고 테스트가 깨졌습니다. 루트에서 `test:run`을 돌리자 sanitize 로직을 가진 패키지가 exit 1로 죽었습니다.

용의자가 너무 많았습니다. pnpm 11 자체일 수도 있고, 새로 해석된 패키지들 중 하나일 수도 있습니다. 그래서 먼저 변경 브랜치와 main을 분리해 main에서는 같은 테스트가 통과하는 것부터 확인해 원인을 이번 변경 집합 안으로 좁혔습니다. 다음으로 main에서 업데이트된 패키지를 하나씩만 올려 테스트를 돌려봤습니다. eslint, vite, vitest, typescript, happy-dom, typescript-eslint, fake-indexeddb, testing-library, dompurify — 아홉 개 중 깨짐을 재현한 것은 dompurify 하나였습니다(typescript-eslint는 lint 회귀였고, 별개로 해결했습니다). 변경 브랜치에서 dompurify만 3.3.1로 되돌리자 테스트도 다시 통과했습니다.

여기까지 오면 결론은 자명해 보입니다. DOMPurify 3.4.11이 무언가를 망가뜨렸다. 릴리스 노트를 뒤지고, 3.3.1로 핀을 박고, upstream에 이슈를 하나 남기면 끝나는 이야기처럼 보였습니다.

이 글은 그 결론이 왜 절반만 맞는지에 대한 이야기입니다. 그리고 그 절반을 가르는 데 쓴 방법이 버전과 환경을 격리하는 실험입니다.

지금 생각해보면 lockfile 삭제는 서로 다른 두 변경을 한 스텝에 섞는 행동이었습니다. pnpm 메이저 전환만이 목적이라면 lockfile을 지우지 않아도 새 pnpm이 포맷을 마이그레이션해 줍니다. 의존성 재해석은 원할 때 따로, 리뷰 가능한 단위로 할 수 있는 작업이었습니다. 이 경계를 섞은 대가로, 어느 변경이 범인인지 하나씩 좁혀가는 비용을 사후에 치렀습니다.

## 두 개의 이상한 실패

처음 마주한 화면은 sanitizer가 아니라 테스트 러너의 죽음이었습니다. 루트에서 `test:run`을 돌리면 prepaint(CSR 첫 화면을 스냅샷으로 복원하는 패키지)가 11개 파일 중 10개, 163개 테스트 중 119개까지 돌다가 Vitest의 unhandled EISDIR 오류를 뱉으며 exit 1로 멈췄습니다. 에러 메시지만 보면 source map 파일을 읽다 실패했다는 내용이라, 이번 재설치로 4.0.18에서 4.1.10이 된 vitest부터 의심했습니다. 하지만 앞의 매트릭스에서 vitest 단독 업데이트는 무해했습니다. 러너 메시지는 표면이고, 그 아래에 다른 실패가 있습니다.

sanitize 테스트 파일만 단독 실행해서 좁히자 실체가 나왔습니다. 44개 중 3개 실패 — 스크립트 태그 제거, HTML sanitize, 안전한 구조 보존. 셋 다 DOMPurify를 실제로 태우는 비동기 경로의 테스트였고, DOMPurify 없이 DOMParser로 도는 fallback 경로 테스트는 전부 통과했습니다.

여기서 코드 구조를 잠깐 설명하면, 문제의 [`safeSetInnerHTML`](https://github.com/joseph0926/firsttx/blob/main/packages/prepaint/src/sanitize.ts)은 내부에서 `sanitizeSnapshotHTML`을 호출하고, 이 함수는 dompurify를 dynamic import해서 성공하면 `DOMPurify.sanitize`를, 실패하면 자체 fallback sanitizer를 태웁니다. 실패한 3개는 전부 DOMPurify 경로였습니다.

실패한 테스트의 입출력을 버전별로 비교하면 이렇습니다.

3.3.1은 기대한 대로 동작합니다.

```html
<div onclick="alert(1)">
  <script>
    evil();
  </script>
  Safe
</div>
→
<div>Safe</div>

<div class="wrapper">
  <p>Paragraph</p>
  <span>Span</span>
</div>
→
<div class="wrapper">
  <p>Paragraph</p>
  <span>Span</span>
</div>
```

3.4.11은 같은 입력에서 이렇게 됩니다.

```html
<div class="wrapper">
  <p>Paragraph</p>
  <span>Span</span>
</div>
→
<p>Paragraph</p>
<span>Span</span>
```

증상이 두 개였습니다.

첫째, 안전한 입력에서 바깥 div가 통째로 사라졌습니다. 위험한 태그도, 위험한 속성도 없는 래퍼 div가 사라지고 자식들만 남았습니다. `class`도 함께 소실됐습니다.

둘째, 위험 입력 쪽은 더 이상했습니다. sanitize 직전에 찍은 입력 로그는 나오는데 출력 로그가 아예 없었습니다. 값이 잘못 나온 게 아니라 로그 줄에 도달하지 못한 것입니다. sanitize 호출을 try/catch로 감싸 보니 에러가 잡혔습니다.

```
Error: Failed to execute 'insertBefore' on 'Node': Only one element on document allowed.
```

sanitize가 잘못된 값을 돌려주는 게 아니라 **던지고** 있었습니다. 그것도 DOMPurify 내부가 아니라 happy-dom의 `HTMLDocument.insertBefore`에서요. 이 스택은 일단 적어두고 넘어갑니다.

먼저 설정부터 확인했습니다. 프로젝트가 `FORBID_TAGS`로 넘기는 위험 태그 목록에 div는 없습니다. script, iframe, form, input 같은 것들뿐입니다. class도 금지 속성이 아닙니다. 그런데 왜 div가 사라질까요.

가설을 두 개 세웠습니다.

1. 3.4.11이 `class` 속성을 위험으로 판정한다
2. 위험 판정된 속성이 있으면 속성만 지우는 게 아니라 요소를 삭제한다

검증은 입력 세 개로 했습니다. A는 class와 커스텀 속성을 함께, B는 커스텀 속성만, C는 속성이 하나도 없는 맨 div — 속성과 무관하게 div가 죽는지 가르는 대조군입니다.

결과는 셋 다 div 소실. 대조군 C까지 죽었으니 속성은 원인이 아닙니다. 가설 1과 2 모두 기각.

div는 속성 때문에 사라진 게 아니었습니다. 속성 수준에서 세운 가설은 전부 기각됐고, 문제는 다른 층에 있었습니다.

## 같은 버전, 다른 환경

막힌 상태에서 config 옵션을 뒤지다 이상한 것을 발견했습니다. sanitize 옵션에 `WHOLE_DOCUMENT: true`를 주자 래퍼 div가 살아 돌아온 것처럼 보였습니다. 문서 전체 반환 여부가 div의 생사를 갈랐습니다.

여기서 가설 3을 세웠습니다. div는 위험 판정으로 삭제된 게 아니라, 반환 범위 밖에 있었던 것 아닐까. DOMPurify는 기본적으로 body 내용만 반환하는데, 3.4.11에서 파싱된 문서 안 div의 위치가 달라졌고 기본 반환 창이 그걸 잘라냈다면 설명이 됩니다.

검증하려면 sanitize의 원시 반환값을 직접 봐야 합니다. 버전 두 개 × 옵션 두 개로 2×2를 채웠습니다.

|                        | 3.3.1                    | 3.4.11                   |
| ---------------------- | ------------------------ | ------------------------ |
| 기본 옵션              | div 유지                 | div 소실, throw 없음     |
| `WHOLE_DOCUMENT: true` | div가 `<body>` 안에 정상 | **throw** (insertBefore) |

이 표가 두 가지를 무너뜨렸습니다.

첫째, `WHOLE_DOCUMENT`는 fix가 아니었습니다. 3.4.11에서 이 옵션을 주면 div가 사는 게 아니라 아예 throw합니다. "고쳐졌다"고 봤던 결과는 3.3.1 쪽 실행에서 본 것을 3.4.11에 잘못 귀속한 것이었습니다. 두 버전을 오가며 실험하다 보면 이런 오귀속이 생각보다 쉽게 생깁니다.

둘째, 가설 3도 그대로는 성립하지 않습니다. 문제는 "어느 조각을 반환하나"가 아니라, 3.4.11이 문서를 조작하는 방식 자체가 어딘가와 충돌하고 있었습니다.

이 시점의 관찰을 다시 모으면 이렇습니다. throw는 happy-dom의 `HTMLDocument.insertBefore`에서 나온다. 에러 메시지는 "document에는 root element 하나만 허용"이다. 즉 DOMPurify 3.4.11은 어떤 이유로 document 노드에 직접 자식을 꽂으려 하고, happy-dom은 그걸 거부한다.

사실 happy-dom을 의심한 건 이번이 처음이 아니었습니다. 더 일찍 "테스트가 happy-dom 위에서 도니까, container가 body 안에 있다는 보장이 없어서 그런 것 아닐까"라는 가설을 세웠다가, 제 로그에 스스로 반박당했습니다. sanitize 출력에 이미 div가 없었으니 container에 넣기 전에 이미 사라진 겁니다. 의심의 방향은 맞았는데 지점이 틀렸습니다.

그래서 이번에는 지점을 제대로 잡고 격리했습니다. 코드도, DOMPurify 버전도, 입력도 전부 고정하고 DOM 구현체 하나만 바꿉니다. happy-dom 대신 jsdom에서 같은 테스트를 돌렸습니다.

```
3.4.11 + jsdom
→ <html><head></head><body><div class="wrapper"><p>Paragraph</p><span>Span</span></div></body></html>
```

던지지도 않고, div도 멀쩡합니다. 3.3.1과 동일한 출력입니다.

이 한 번의 실행으로 그림이 뒤집혔습니다. DOMPurify 3.4.11은 단독으로는 무죄입니다. 같은 버전, 같은 코드, 같은 입력이 jsdom에서는 정상이고 happy-dom에서만 깨집니다. 범인은 버전이 아니라 3.4.11 × happy-dom이라는 조합입니다.

글 첫머리에서 dompurify를 범인으로 지목한 결론이 절반만 맞았다고 한 이유가 이것입니다. 패키지 단위 격리는 어느 변경이 트리거인지 알려주지만, 무엇이 원인인지는 알려주지 않습니다. 트리거는 dompurify 업그레이드가 맞습니다. 하지만 원인은 새 버전이 테스트 DOM 구현체와 상호작용하는 방식에 있었습니다.

다만 바깥에서 관찰해 세울 수 있는 가설은 여기까지였습니다. 속성 가설도, 직렬화 경계 가설도 기각됐고, 3.4.11이 document를 조작하는 이유는 동작만 봐서는 보이지 않았습니다. 소스를 열었습니다.

## tagName이 빈 문자열이 되는 사슬

두 버전의 `purify.ts`를 대조하면서 의심 가는 diff를 몇 개 짚었지만, 노드 제거 로직 자체는 두 버전이 사실상 같았습니다. DOMPurify는 허용 목록에 없는 요소를 만나면 그 자식들을 부모 자리로 끌어올리고(keep-content) 요소만 제거합니다. 이 동작은 3.3.1에도 있습니다.

대신 출력을 다시 보다가 익숙한 모양을 발견했습니다. `<div class="wrapper"><p>…</p><span>…</span></div>`가 `<p>…</p><span>…</span>`이 되는 것은, div가 **허용되지 않은 태그로 판정돼 자식만 끌어올려지고 제거된 결과**와 정확히 같은 모양입니다. WHOLE_DOCUMENT의 throw도 같은 논리로 읽힙니다. `<html>`이 허용되지 않은 태그로 판정되면 그 자식인 head와 body를 부모, 즉 document에 꽂아야 하는데, happy-dom은 document에 root element를 하나만 허용하므로 거부합니다.

두 증상이 하나의 문장으로 모입니다. 3.4.11은 div와 html 같은 **기본 허용 태그를 허용되지 않은 것으로 오판**하고 있습니다.

그러면 태그 이름 판정 코드가 용의자입니다. 여기에 두 버전의 실제 diff가 있었습니다. 3.3.1은 요소 이름을 `currentNode.nodeName`으로 직접 읽습니다. 3.4.11은 모듈 로드 시점에 `Node.prototype`에서 nodeName의 getter 함수를 미리 뽑아 캐시해두고, 매번 그 getter를 노드에 적용하는 `getNodeName` 경로로 바뀌었습니다.

정말 여기서 갈리는지 확인하기 위해 `uponSanitizeElement` 훅으로 DOMPurify가 계산한 태그 이름을 그대로 찍어봤습니다.

| div에 대해                 | happy-dom | jsdom   |
| -------------------------- | --------- | ------- |
| DOMPurify가 계산한 tagName | `""`      | `"div"` |
| `node.nodeName` 직접 접근  | `"DIV"`   | `"DIV"` |

노드 자체는 멀쩡합니다. 직접 물어보면 양쪽 다 `"DIV"`라고 답합니다. 그런데 happy-dom에서 DOMPurify가 계산한 값만 빈 문자열입니다. 범인은 노드가 아니라 **이름을 읽는 경로**입니다.

경로가 왜 갈리는지는 프로토타입 레벨별로 getter를 직접 호출해보면 드러납니다.

```js
const nodeGet = Object.getOwnPropertyDescriptor(Node.prototype, 'nodeName').get;
const elGet = Object.getOwnPropertyDescriptor(
  Element.prototype,
  'nodeName',
)?.get;

div.nodeName;
nodeGet.call(div);
elGet?.call(div);
```

| nodeName getter를 div에 호출 | happy-dom | jsdom            |
| ---------------------------- | --------- | ---------------- |
| `Element.prototype`의 getter | `"DIV"`   | 정의 자체가 없음 |
| `Node.prototype`의 getter    | `""`      | `"DIV"`          |

jsdom은 DOM spec대로 nodeName getter를 `Node.prototype` 한 곳에만 둡니다. getter 하나가 노드 타입을 보고 올바른 이름을 돌려주므로, 어느 경로로 읽어도 같은 값이 나옵니다.

happy-dom은 nodeName을 두 레벨에 정의합니다. `Element.prototype`의 오버라이드가 진짜 태그 이름을 돌려주고, `Node.prototype`의 base getter는 element에 대해 빈 문자열을 돌려줍니다. 일반적인 속성 접근 `div.nodeName`은 프로토타입 체인을 인스턴스에서 가까운 쪽부터 걷다가 처음 만나는 getter를 쓰기 때문에 Element 쪽이 이기고, 값도 옳습니다. 하지만 DOMPurify처럼 `Node.prototype`에서 getter를 뽑아 고정해두면, 체인을 걷지 않고 Node 레벨의 base getter를 직접 호출하게 됩니다. 두 레벨이 갈라진 구현에서만 두 읽기 방식의 답이 갈라집니다.

이제 사슬 전체가 연결됩니다.

1. happy-dom이 nodeName을 두 레벨에 정의하고, Node 레벨 getter는 element에 `""`를 반환한다
2. DOMPurify 3.4.x가 `Node.prototype`에서 뽑아 캐시한 getter로 이름을 읽는다
3. 모든 요소의 tagName이 `""`로 계산된다
4. `""`는 허용 목록에 없으므로 모든 요소가 제거 대상이 된다
5. keep-content 동작으로 자식을 끌어올리고 요소를 제거한다
6. 기본 옵션에서는 래퍼 div가 사라지고, WHOLE_DOCUMENT에서는 html의 자식을 document에 꽂으려다 happy-dom의 root element 제한에 걸려 throw한다

3.3.1이 무사했던 이유도 같은 사슬로 설명됩니다. `currentNode.nodeName` 직접 접근은 체인을 걸어 Element 오버라이드를 쓰므로 올바른 이름을 얻습니다.

덧붙이면 happy-dom 안에서도 nodeName은 이례적인 패턴입니다. nodeType이나 parentNode 같은 다른 속성들은 getter가 인스턴스에 저장된 값을 읽는 구조라 어느 레벨에서 호출해도 옳은 값이 나오는데, nodeName만 base가 `""`를 돌려주는 stub이고 Element가 오버라이드하는 구조였습니다. 실패가 이렇게까지 특정적이었던 이유입니다.

남은 의문은 하나입니다. DOMPurify는 왜 `div.nodeName`으로 읽으면 되는 것을 굳이 프로토타입에서 getter를 뽑아 쓰는 우회로로 바꿨을까 — 이것은 버그가 아니라 의도된 방어였습니다.

## 인스턴스를 믿을 수 없어서 생긴 방어

DOMPurify가 `div.nodeName` 대신 프로토타입에서 뽑은 getter를 쓰는 이유는 DOM clobbering이라는 공격을 막기 위해서입니다.

sanitizer가 다루는 HTML은 정의상 공격자가 만들었을 수 있는 입력입니다. 그리고 HTML은 마크업만으로 DOM의 속성 조회 결과를 오염시킬 수 있습니다.

```html
<form>
  <input name="nodeName" />
</form>
```

실제 브라우저에서 이 form 요소의 `nodeName`을 읽으면 문자열 `"FORM"`이 아니라 방금 그 input 요소가 나옵니다. HTMLFormElement는 자식 컨트롤을 name으로 접근하는 named property를 지원하고, 이 조회가 내장 속성보다 우선하기 때문입니다. sanitizer가 `node.nodeName`을 그대로 믿는다면, 공격자는 마크업만으로 이름 판정을 속일 수 있습니다.

그래서 DOMPurify 3.4.x가 택한 것이 앞서 본 getter 캐시입니다. 인스턴스가 아무리 오염돼도 프로토타입의 getter는 마크업으로 덮어쓸 수 없으니, spec을 따르는 DOM에서는 항상 진짜 이름이 나옵니다.

처음에 저는 반대로 생각했습니다. 실제 브라우저처럼 제대로 된 DOM이라면 인스턴스를 믿어도 되지 않느냐고. 방향이 거꾸로였습니다. clobbering이 실제로 일어나는 곳이 바로 실제 브라우저입니다. 공격자 HTML 앞에서 인스턴스 접근은 실제 DOM일수록 믿을 수 없고, 그것이 이 우회 전략의 존재 이유입니다. 흥미로운 것은 happy-dom에서 위 form 실험을 돌리면 여전히 `"FORM"`이 나온다는 점입니다. happy-dom은 이 방어가 막으려는 clobbering조차 재현하지 않습니다.

정리하면 DOMPurify의 전략은 "DOM이 spec을 따른다"는 가정 위에서 완전히 옳습니다. 브라우저와 jsdom에서 이 가정은 성립합니다. 깨지는 곳은 nodeName을 spec과 다르게 두 레벨로 정의한 happy-dom뿐입니다. 보안을 강화한 변경이, 그 보안의 전제를 지키지 않는 환경에서 무너진 것입니다.

제목의 답이 여기서 나옵니다. DOMPurify는 옳은 가정 위에서 옳은 방어를 하고 있으므로, 고칠 곳은 DOMPurify가 아니라 happy-dom의 nodeName입니다.

다만 이것을 "테스트 환경에서만 깨지는 문제"로 정리하고 덮기에는, 깨짐의 성격이 좋지 않았습니다.

## 조용한 실패가 향하는 방향

지금까지의 사슬만 보면 이 버그는 과잉 제거처럼 보입니다. 모든 요소가 제거 대상으로 판정되니, 지워지지 말아야 할 div까지 지워지는 시끄러운 실패고, 테스트가 바로 잡아냅니다.

그런데 출력을 다시 보면 이상한 점이 있습니다. 전 요소가 제거 대상으로 판정됐는데 `<p>`와 `<span>`은 태그째 살아남았습니다. 모든 요소를 지우기로 한 sanitizer의 출력에 요소가 남아 있습니다.

프로브를 붙여 순회를 관찰하면 더 이상합니다. span은 검사 자체를 받지 않았습니다. 자식을 끌어올리고 요소를 제거하는 재배열이 반복되는 동안 순회가 어긋나서, 일부 노드가 방문되지 않은 채 출력으로 통과하는 것으로 보입니다. 이 내부 경위까지 전부 파고들지는 않았지만, 관찰된 사실만으로 방향은 분명합니다.

과잉 제거는 화면이 깨져 바로 눈에 띄는 실패입니다. 반대로 검사를 건너뛴 통과는 위험한 것을 남기는 조용한 실패입니다. 실제로 같은 조합을 다른 입력으로 재현하면 위험 입력의 script 태그가 소독되지 않은 채 출력에 남는 경우가 확인됩니다. upstream에도 같은 증상 보고가 있습니다. happy-dom 쪽에는 [부모만 sanitize되고 자식이 처리되지 않는다는 이슈](https://github.com/capricorn86/happy-dom/issues/1810)가, DOMPurify 쪽에는 [허용 목록에 없는 중첩 요소가 제거되지 않고 남는다는 이슈](https://github.com/cure53/DOMPurify/issues/1094)가 있는데, 둘 다 원인 진단 없이 증상만 보고돼 있었습니다. tagName이 빈 문자열이 되는 사슬로 읽으면 같은 뿌리로 설명됩니다.

정리하면 이 조합에서 sanitizer는 허용 목록 기반 소독기에서 일부 노드를 조용히 놓치는 필터에 가까워집니다. 테스트 몇 개가 깨지는 불편이 아니라, sanitize 결과를 신뢰할 수 없게 되는 문제입니다.

다만 경계는 정확히 긋겠습니다. firsttx에서 이 sanitize 코드가 실제로 도는 곳은 브라우저입니다. 테스트만 happy-dom 위에서 돌고 있었으므로 이 사건 자체는 production에 영향이 없습니다. 위험해지는 경우는 happy-dom을 서버 사이드 DOM으로 삼아 sanitize를 돌리는 구성입니다. DOMPurify 공식 문서도 서버에서는 jsdom을 권장하고 happy-dom 사용은 권장하지 않습니다.

그래서 결론이 "3.3.1로 핀 박고 끝"이 되지 않았습니다. 제 레포는 핀으로 막을 수 있지만 같은 사슬을 밟을 다른 사용자들이 있고, 원인 진단은 upstream 어디에도 없었습니다. 적어도 그때는 그렇게 보였습니다.

## 그래서 어디를 고쳤나

firsttx 자체의 조치는 간단했습니다. dompurify를 3.3.1로 고정하고, 이번 작업의 원래 목표였던 pnpm 11 전환을 마저 끝냈습니다. DOMPurify 최신 호환은 별도 작업으로 분리했습니다. 진행 중에 발견한 문제를 지금 작업의 범위로 끌어들이지 않는 것도 이번에 의식적으로 지키려 한 경계입니다.

남은 것은 upstream입니다. 우선 최신 버전에서 이미 고쳐졌는지부터 확인했습니다. happy-dom을 당시 최신인 20.10.6까지 올려도 프로브 결과와 throw가 그대로 재현됐습니다. nodeName의 2-레벨 구조는 오타가 아니라 클래스 계층 설계여서, 버전이 올라도 그대로 남아 있었습니다.

fix의 모양도 좁혀뒀습니다. happy-dom 내부에서도 nodeName만 이례적인 stub과 오버라이드 패턴이었으므로, 다른 속성들처럼 노드 타입을 보고 이름을 돌려주는 방식으로 Node 레벨 getter를 바꾸면 되는 국소적인 수정입니다. happy-dom 쪽에서도 DOMPurify 호환을 [공식적으로 추적하는 이슈](https://github.com/capricorn86/happy-dom/issues/1629)가 Security milestone에 올라 있었습니다.

여기까지 정리하고 기여를 준비하다가 해프닝이 하나 있었습니다. 조사 시점의 검색으로는 원인 진단을 찾지 못해 "이 진단은 upstream에 없다"고 판단했는데, 이후 교차 확인에서 [같은 진단의 이슈](https://github.com/capricorn86/happy-dom/issues/2182)와 [같은 방향의 fix PR](https://github.com/capricorn86/happy-dom/pull/2183)이 한 달 전부터 열려 있었던 것을 발견했습니다. 일반 웹 검색 두 번으로는 랭킹에 밀린 이슈를 놓칠 수 있었고, "없다"는 판단은 저장소 이슈 트래커 안에서 직접 검색한 뒤에 내렸어야 했습니다. 대신 독립적으로 같은 진단에 도달해 있었다는 확인은 됐고, 기여 방향은 새 이슈를 여는 것에서 열려 있는 PR에 재현 근거를 보태는 쪽으로 바꿨습니다.

## 정리

이번 사건에서 가져가는 판단 규칙은 세 개입니다.

1. lockfile을 지우고 재설치하는 것은 도구 전환과 의존성 전체 재해석을 한 스텝에 섞는 일입니다. 둘 다 의도한 게 아니라면 분리합니다.
2. 되돌려서 고쳐지는 것은 트리거 확인이지 원인 확정이 아닙니다. 버전 축과 환경 축을 하나씩 격리해야 원인이 나옵니다.
3. 테스트의 통과와 실패는 테스트 환경의 함수입니다. 특히 DOM은 구현체에 따라 갈리므로, 깨짐을 라이브러리 버그로 단정하기 전에 production이 실제로 도는 환경에서 재현되는지 확인합니다.

DOMPurify를 업그레이드했는데 고칠 곳은 happy-dom이었습니다. 같은 증상을 만난 분에게 이 글이 진단의 지름길이 되면 좋겠습니다.
