# 전역 AGENTS.md는 정말 프로젝트 문서 예산을 잡아먹을까

## 32 KiB는 어디까지 세는가

저는 Claude Code, Codex, Copilot 세 도구용 전역 지침을 파일당 200줄 상한으로 관리하고 있습니다. 최근 전역 지침을 정리하면서 로컬 위키의 Codex 문서를 린트했고, 그 과정에서 Codex가 `project_doc_max_bytes` 설명의 범위를 짚었습니다.

> 여기서 전체 크기가 전역과 프로젝트를 모두 뜻하는지, 프로젝트 문서만 뜻하는지 확인이 필요하다.

Codex는 `~/.codex/AGENTS.md`(전역)와 저장소의 `AGENTS.md`(프로젝트)를 이어붙여 프롬프트에 넣는데, 이때 `project_doc_max_bytes`라는 설정이 기본 32 KiB의 크기 제한으로 작동합니다. 문제는 이 한도가 **어디까지를 세는지**입니다.

[AGENTS.md 가이드](https://learn.chatgpt.com/docs/agent-configuration/agents-md)는 전역 지침과 프로젝트 지침을 차례로 설명한 뒤, 문서의 "combined size"가 `project_doc_max_bytes`에 도달하면 파일 추가를 멈춘다고 적습니다. 이 문장만으로는 전역 파일도 합산하는지 알기 어렵습니다. 같은 공식 문서의 [설정 레퍼런스](https://learn.chatgpt.com/docs/config-file/config-reference)는 이 값을 "project instructions"를 만들 때 읽는 최대 바이트라고 설명합니다. 프로젝트 범위라는 힌트는 있지만, 전역 `AGENTS.md`가 계산에서 제외된다고 명시하지는 않습니다. [고급 설정 문서](https://learn.chatgpt.com/docs/config-file/config-advanced)는 다시 "각 `AGENTS.md` 파일에서 얼마나 읽을지"라고 표현합니다. 공식 페이지마다 설명이 조금씩 달라 문장만으로 실제 적용 범위를 확정하기 어려웠습니다.

저는 전역과 프로젝트를 합친 크기라고 이해하고 있었습니다. 같은 해석을 바탕으로 전역 파일을 줄이라고 권하는 [설정 가이드](https://thepromptshelf.dev/blog/agents-md-codex-setup-guide-2026/)도 있었습니다. "Every byte in `~/.codex/AGENTS.md` is a byte that cannot be used by project-level files"라면서, 전역 파일을 2~3 KB 아래로 유지하라는 권장까지 붙입니다.

그리고 제가 운영하는 로컬 위키의 Codex 페이지에도 이렇게 적혀 있었습니다.

> 빈 파일은 무시, 전체 크기는 `project_doc_max_bytes`(기본 32 KiB) 제한

"전체 크기"라고 적은 시점에 저도 같은 해석을 하고 있었던 겁니다. 전역과 프로젝트를 합친 전체가 32 KiB 안에 들어가야 한다고.

이 계산대로라면 제 전역 AGENTS.md부터 줄여야 했습니다. 당시 파일 크기는 21,547바이트였습니다. 기본 한도 32,768바이트에서 전역을 빼면 프로젝트 문서에는 11 KiB 정도만 남기 때문입니다.

더 헷갈렸던 이유는 파일이 **조용히** 잘리기 때문입니다. [Codex 저장소에는 AGENTS.md가 경고 없이 잘린다는 이슈](https://github.com/openai/codex/issues/7138)가 올라와 있습니다. 사용 중에는 어느 파일이 얼마나 잘렸는지 알기 어려웠고, 그래서 위 해석도 확인하지 않은 채 받아들이고 있었습니다.

직접 측정해보니 이 해석은 틀렸습니다.

## 프롬프트를 직접 열어보는 명령

Codex에는 모델 입력을 확인하는 명령이 있습니다.

```bash
codex debug prompt-input
```

이 명령은 모델에게 보이는 입력 메시지 목록을 JSON으로 출력합니다. 스킬 목록, 권한 지침, 그리고 AGENTS.md가 어떻게 합쳐져 들어가는지가 메시지 단위로 그대로 보입니다. AGENTS.md 체인은 `# AGENTS.md instructions for <경로>`로 시작하는 하나의 developer 메시지로 들어갑니다.

여기에 `-c` 플래그로 설정을 세션 한정으로 덮어쓸 수 있습니다.

```bash
codex debug prompt-input -c project_doc_max_bytes=5000
```

`project_doc_max_bytes`를 바꿔가며 AGENTS.md 블록의 바이트 크기를 재면, 한도가 무엇에 적용되는지 역산할 수 있습니다.

## 실험 설계

먼저 측정 조건을 적어두겠습니다.

- codex-cli 0.147.0, 2026-08-12
- 실행 위치: 저장소 root의 한 단계 아래 디렉터리. 이 위치에서는 저장소 root의 `AGENTS.md`(10,563 B)와 현재 디렉터리의 `AGENTS.md`(11,696 B)가 체인에 들어갑니다. 합계는 22,259 B입니다
- 전역 `~/.codex/AGENTS.md`: 21,547 B
- 측정 대상: 출력 JSON에서 `# AGENTS.md instructions`로 시작하는 메시지 텍스트의 UTF-8 바이트 수

`project_doc_max_bytes`를 4개 값으로 바꿔 관측하고, 그 관측으로 모델을 세운 뒤, 나머지 값에서 모델의 예측이 맞는지 확인하는 순서입니다.

## 측정 결과

|                limit | 관측 블록 | 모델 예측 |
| -------------------: | --------: | --------: |
|                5,000 |  26,675 B |  26,677 B |
|               15,000 |  36,679 B |  36,677 B |
|               20,000 |  41,677 B |  41,677 B |
| 25,000 / 기본 32,768 |  43,936 B |  43,936 B |

관측값을 가장 단순하게 설명하는 모델은 이랬습니다.

```
블록 크기 = 전역(21,547 B, 한도 무관)
          + min(프로젝트 문서 합계, project_doc_max_bytes)
          + wrapper(130 B)
```

읽는 방법은 이렇습니다. limit을 5,000으로 내리면 블록은 26,675 B가 됩니다. 전역 21,547에 5,000과 wrapper를 더한 값입니다. limit을 10,000 올리면 블록도 정확히 10,000 커집니다. 그리고 limit이 프로젝트 문서 합계(22,259 B)를 넘어서면 블록은 43,936 B에서 더는 자라지 않습니다.

첫 행만 보면 적용 범위를 알 수 있습니다. **limit 5,000은 전역 파일 크기 21,547보다 작습니다.** 전역이 한도에 포함된다면 이 설정에서 전역부터 잘려야 합니다. 하지만 블록에는 전역 파일 전문이 들어 있었고, 프로젝트 문서가 5,000바이트에서 잘렸습니다.

`project_doc_max_bytes`가 제한하는 쪽은 프로젝트 문서였습니다. 전역은 이 예산에서 빠지고 전문이 들어갑니다.

예측과 관측의 차이는 최대 2바이트였습니다. 뒤의 재검증에서 확인했듯 wrapper가 상수가 아니고, 구현도 바이트 단위로 자른 값을 손실 UTF-8 문자열로 바꾸므로 이 작은 잔차를 한 원인으로 단정하지 않았습니다. 이 실험에서 필요한 판별은 전역이 한도에 포함되는지였고, 그 결론에는 영향을 주지 않습니다.

## 사흘 뒤, 조건이 바뀐 상태로 재검증

이 글을 쓰기 전에 같은 측정을 다시 돌렸습니다. 2026-08-15, CLI 버전은 같은 0.147.0. 그런데 그 사이 파일들이 바뀌어 있었습니다. 전역은 21,547에서 23,284 B로, root AGENTS.md는 10,563에서 10,741 B로. 모델 입장에서는 한 번도 본 적 없는 입력입니다. 모델이 진짜라면 새 숫자로도 맞아야 합니다.

이번에는 저장소 root에서 실행했습니다.

|       limit | 관측 블록 | 모델 예측 |
| ----------: | --------: | --------: |
|       5,000 |  28,403 B |  28,403 B |
|      15,000 |  34,144 B |  34,144 B |
|      20,000 |  34,144 B |  34,144 B |
| 기본 32,768 |  34,144 B |  34,144 B |

4개 값 모두 바이트 단위로 일치했습니다. limit 5,000에서 전역(23,284 B)이 전문 그대로 들어 있는 것도 부분 문자열 검사로 다시 확인했습니다.

재검증 과정에서 처음 측정 때 놓쳤던 사실도 두 개 드러났습니다.

첫째, **"프로젝트 문서 합계"의 범위는 실행 위치가 정합니다.** root에서 실행하자 15,000 이상에서 블록이 34,144 B에서 멈췄습니다. 전역 23,284에 root AGENTS.md 10,741 하나만 더한 크기입니다. 하위 디렉터리의 11,696 B짜리 AGENTS.md는 체인에 아예 없었습니다. Codex는 저장소 root부터 **현재 디렉터리까지** 내려오며 파일을 줍기 때문에, root에서 실행하면 하위 문서는 애초에 후보가 아닙니다. 같은 저장소라도 어디서 실행하느냐에 따라 예산을 쓰는 문서 집합이 달라집니다.

둘째, wrapper는 상수가 아니라 체인 구성의 함수였습니다. 1개 문서 체인에서는 119 B, 2개 문서 체인에서는 130 B. 헤더에 경로 문자열이 들어가고 문서 사이 구분자가 붙으니 당연한 결과인데, 처음 측정에서는 한 가지 구성만 봐서 상수처럼 보였던 겁니다.

## 그래서 줄여야 할 것은 무엇이었나

처음에는 전역이 21 KiB나 되니 전역부터 줄여야 프로젝트 문서가 안전하다고 생각했습니다. 측정하고 나서는 저장소 문서를 먼저 보게 됐습니다.

문제의 저장소는 프로젝트 체인 합계가 22,437 B로 **기본 한도의 68%**를 이미 쓰고 있습니다. 남은 예산은 10,331 B라 비슷한 크기의 AGENTS.md를 하위 디렉터리에 하나 더 두면 한도를 넘습니다. 이쪽이 실제로 줄이거나 감시해야 할 대상이었습니다.

물론 전역 파일도 매 세션 입력에 포함되므로 컨텍스트 토큰을 씁니다. 전역 파일의 크기를 관리할 이유는 여전히 있습니다. 다만 그 비용과 `project_doc_max_bytes`에 따른 프로젝트 문서 잘림은 별개의 문제였습니다. 둘을 한 문제로 보면 "전역을 줄이면 프로젝트가 안 잘린다"라는, 측정과 어긋나는 처방이 나옵니다.

위키의 그 문장도 재현 절차와 함께 고쳤습니다. "전체 크기는 32 KiB 제한"을 "한도는 root부터 실행 위치까지의 프로젝트 체인 합계에만 적용되고 전역은 합산되지 않는다"로 바꿨습니다. 이 오독은 2026-05-30에 적혀 실측까지 두 달 넘게 위키에 있었고, 그동안 저는 그 문장을 근거로 전역 다이어트를 고민했습니다.

이 측정을 처음부터 따로 계획했던 건 아닙니다. 지난 3개월 동안 실제 작업에서 생긴 실패 251건을 모아 전역 규칙을 다시 검토하고 있었습니다. 규칙 후보 18건을 살펴보면서 같은 실패가 두 번 나타나야 고치는 2-strike 기준을 적용했고, 근거가 약한 3건은 폐기했습니다.

그중 하나가 "전역 200줄 상한이 프로젝트 문서 예산과 경쟁한다"는 항목이었습니다. 전제를 확인한 결과, 이 항목은 수정 목록에서 뺐습니다.

## 측정 한 번이 바꾼 것

사용하면서 잘림을 알아차릴 방법이 없었고, AGENTS.md 가이드의 "combined size"만으로는 어느 범위인지 분명하지 않았습니다. 설정 레퍼런스에는 프로젝트 지침의 한도라는 힌트가 있었지만, 전역 파일이 제외된다는 설명은 없었습니다. 공식 페이지마다 표현도 달랐고, 제가 읽은 외부 가이드와 위키에는 한쪽 해석만 적혀 있었습니다. 저도 몇 달 동안 그 문장을 기준으로 판단했습니다.

확인에는 명령 한 줄이면 충분했습니다.

```bash
codex debug prompt-input -c project_doc_max_bytes=5000
```

출력에서 `# AGENTS.md instructions`로 시작하는 메시지를 찾아 크기를 재고, limit을 바꿔가며 몇 번 반복하면 끝입니다. 전역 파일보다 작은 limit을 줬는데 전역이 통째로 들어 있는 것을 눈으로 확인하는 순간, 두 달짜리 오독이 5분 만에 끝났습니다.

지침 파일을 줄이면 그 규칙이 막던 실수가 다시 생길 수 있습니다. 이번에는 어느 파일이 예산에 포함되는지 확인하지 않은 채 전역 지침부터 줄일 뻔했습니다. 앞으로는 지침 파일을 손대기 전에 같은 명령으로 실제 잘림부터 확인하려고 합니다.
