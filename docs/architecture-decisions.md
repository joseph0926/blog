# 아키텍처 결정

코드만으로는 선택 이유를 복구하기 어려운 결정을 기록합니다.

## 필터 URL은 서버에서 렌더링한다

`?category`, `?q`, `?year`가 붙은 글 목록도 서버에서 데이터를 채워 내려보내고 검색 엔진이 읽을 수 있어야 합니다. 정적 화면과 클라이언트 필터만 사용하는 대안은 필터별 서버 렌더링을 포기하므로 선택하지 않았습니다.

이 결정 때문에 `apps/blog/src/app/[locale]/blog/page.tsx`는 `searchParams`를 읽고 요청 시점에 렌더링합니다. 렌더링 범위를 최적화하더라도 필터 결과의 서버 렌더링은 유지해야 합니다.

## 서버와 클라이언트는 같은 query identity를 사용한다

서버가 미리 가져온 데이터와 클라이언트가 구독하는 데이터는 같은 필터 정규화와 query 입력을 사용합니다. 둘을 따로 만들면 같은 데이터를 서로 다른 캐시 항목으로 취급할 수 있으며, 과거에 실제 query cache 불일치로 이어졌습니다.

현재 공통 입력은 `apps/blog/src/lib/post-query.ts`가 소유합니다. 공통 정의를 확장할 때도 서버 prefetch와 클라이언트 hook이 서로 다른 query identity를 만들지 않아야 합니다.

## 무한 스크롤이 있는 동안 tRPC를 유지한다

글 목록의 `fetchNextPage`는 클라이언트 상호작용이므로 현재 구조에서는 tRPC와 TanStack Query를 유지합니다. 순수 Server Component와 Server Action만 사용하는 대안은 이 상호작용을 충분히 대체하지 못합니다.

대가로 서버와 클라이언트 사이에 별도의 API·캐시 계층을 유지해야 합니다. 무한 스크롤 요구가 사라지면 이 비용을 계속 감수할 이유도 다시 검토합니다.
